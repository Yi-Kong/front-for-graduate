# shadcn-vue 合规整改 · 修改代价评估

- 评估时间：2026-10-04
- 评估对象：`docs/2026-10-04-shadcn-vue组件合规检查报告.md` 列出的全部整改项
- 结论基调：**整改代价高度分化**——P0 工程安全几乎零代价必须立刻做；P2 规范清理便宜且安全；P1 的"全量替换 27 个业务文件"代价极高且边际收益有限，应改为"选择性替换 + 主题对齐"。

---

## 一、代价评估维度

| 维度 | 含义 |
|---|---|
| 工作量 | 改动代码量 / 文件数 / 需手搓的组件数 |
| 风险 | 改坏现有视觉或交互、引入回归的可能性 |
| 波及面（blast radius） | 改一处会牵动多少页面 / 多少人日验证 |
| 前置依赖 | 必须先做完才安全的事（如先对齐主题再替换组件） |
| 边际收益 | 做完后实际多出来的价值（a11y / 一致性 / 可维护性） |

## 二、逐项代价表

### P0 — 工程安全（必做、零视觉代价）

| 动作 | 文件/命令 | 代码量 | 风险 | 代价 |
|---|---|---|---|---|
| 声明运行时依赖 | `bun add reka-ui @internationalized/date`（1 条命令，改 `package.json` + 锁文件） | 0 业务代码 | 极低 | **极低**（<0.5h） |
| 验证 `bun run build` | 1 次构建 | — | 极低 | 极低 |

> ⚠️ 触发条件已核实：当前 dev 安装能跑（`node_modules` 里有 reka-ui），所以本地开发**暂时不爆**；风险只在 `bun install --production` 或移除 shadcn-vue CLI 时显现（生产部署 / CI 才中招）。**忽略它的代价远高于动手代价**——一旦触发就是"构建直接失败，全站起不来"，而修复只是加一条依赖。

## 三、两条路线对比

### 路线 A：最小合规（推荐）
只做"补齐 + 清理 + 对齐"，**不**大范围重写已有 UI：

1. P0：`bun add reka-ui @internationalized/date`（必做）
2. P1 主题：对齐 `--primary`/`--ring`/`--accent` 到山能红
3. P1 组件：补齐缺失 shadcn 组件，**但只在"新写/新弹窗"时强制使用**；存量 10 个弹窗/抽屉一次性替换为 Dialog/Sheet（a11y 收益最大、范围可控）
4. P2：收敛重复 `.act`/`.pg`/`.kv`、抽 `StatusBadge`/`Pagination`

- **总代价**：约 **3–5 天**（含验证）
- **总风险**：低–中
- **收益**：依赖安全 + 主题统一 + 弹窗/抽屉自带 a11y + 规范清理；后续新页面天然合规
- **代价比**：高（每投入 1 天 ≈ 明显可见的合规/安全提升）

### 路线 B：全量替换
把 27 个业务文件的按钮/输入/表格/弹窗/抽屉**全部**换成 shadcn 组件：

- **总代价**：约 **8–15 天**（含拆分子组件以满足 ≤300 行红线、逐页视觉回归）
- **总风险**：高（大量定制样式在机械替换后需重调；回归面极大）
- **收益**：视觉 100% 来自 shadcn；但**本项目手写 Tailwind + 山能红的设计体系已经相对统一**，shadcn 默认样式反而要重新"染成"山能红 → 边际收益被严重稀释
- **代价比**：低（投入大、多数收益路线 A 已覆盖）

> 关键判断：**"所有组件都用 shadcn" 的真正障碍不是组件缺失，而是它和现有山能红设计体系是两套视觉语言**。要么保留 shadcn 组件但逐个覆写成山能红（等于手写二次样式），要么把全站改成 shadcn 默认风格（破坏设计稿）。无论哪条，全量替换都贵且不一定更美。因此建议路线 A。

## 四、容易被低估的隐性代价

1. **单文件 ≤300 行红线**：`ImportUsers.vue`(301)、`AcademicYear.vue`(309) **已经超限**，任何对它们的整改都会撞线，必须先拆子组件。全量替换会新增更多超限文件。
2. **scoped 样式差异**：6 处 `.act` 局部版与全局版**配色已漂移**（如 `OperationLog.vue` 默认 `#c0202e` vs 全局 `#4b5563`）。直接删局部块会让这些页面视觉回退 → 必须先 diff 合并。
3. **回归验证面**：80 处按钮、22 处输入、6 处表格分散在 27 个文件，任何批量替换都需逐页人肉回归（或写 Edge+CDP 脚本，但脚本本身也要 1–2 天）。
4. **重连 shadcn-vue.com 不稳定**：本次实测可达（200），但历史记录沙箱连不上。新增组件若依赖官方 `add`，需预备离线手写方案，否则会卡住。
5. **`<style scoped>` 清理的连锁**：删除局部 `.act` 后，若该页原本靠局部版覆盖某字段宽度/对齐，全局版未必一致，需逐处确认。

## 五、建议的执行顺序（最小代价拿到最大合规）

| 步骤 | 内容 | 优先级 | 预计 |
|---|---|---|---|
| 1 | `bun add reka-ui @internationalized/date` + build 验证 | P0 立即 | <0.5h |
| 2 | 主题令牌对齐山能红 + grep 核查 `bg-primary` 依赖 | P1 前置 | 0.5 天 |
| 3 | 补齐 dialog/alert-dialog/sheet/input/label/select/textarea/table/badge 等缺失组件 | P1 | 1–2 天 |
| 4 | 优先替换 10 个弹窗/抽屉为 Dialog/Sheet（a11y 收益最大） | P1 选择性 | 1–2 天 |
| 5 | 收敛重复 `.act`/`.pg`/`.kv` + 抽 StatusBadge / Pagination | P2 | 1 天 |
| 6 | 新页面/新弹窗强制用 shadcn；存量 80 按钮/22 输入随需求渐进替换，不做专项全量改写 | 长期 | — |

> 第 6 条是降低代价的关键：**不立项"全量替换"，而是让 shadcn 成为新代码的默认，存量随迭代自然收敛**。这样路线 A 的 3–5 天是一次性投入，之后无需反复大改。

## 六、一句话结论

- **现在就必须做、几乎零代价**：P0 声明依赖。
- **便宜且安全、顺手做了**：P2 规范清理 + 主题对齐。
- **值得做但选范围**：把 10 个弹窗/抽屉换成 Dialog/Sheet。
- **不值得立项**：把 27 个文件的 80 个按钮 / 22 个输入全量改成 shadcn——代价高、收益被现有山能红体系稀释，且会引爆 300 行红线与回归面。

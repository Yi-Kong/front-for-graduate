# 后端文档一致性核对

**核对对象**
- `docs/backend-interface-analysis.md`——《后端接口分析报告（基于实际代码）》，2026-09-16 由代码分析生成，带权限标注与风险标注。
- `docs/API接口文档.md`——《毕业设计督导系统 API 接口文档》，由 OpenAPI schema 自动生成。

**核对时间**：2026-10-01

---

## 一、两文档定位差异（先认清口径）

| 维度 | backend-interface-analysis.md | API接口文档.md |
|---|---|---|
| 来源 | 人工读后端代码 | drf-spectacular 生成的 schema |
| 是否含权限 | 是（逐接口标注 IsAdmin/IsAuthenticated/IsStudent/角色过滤） | 否 |
| 是否含风险标注 | 是（越权、断路、死状态等） | 否 |
| 是否含枚举语义说明 | 部分（指出死状态） | 是（列出全部枚举值，但未区分是否可用） |

> 两文档**本就不是同一性质**的文档：一个是"带风险眼光的代码分析报告"，一个是"纯契约文档"。因此"完全一致"不是合理预期；应核对的是**接口集合与契约字段是否互相矛盾**。

---

## 二、接口覆盖核对（结论：基本覆盖完整，无遗漏）

backend 分析列出的全部业务接口（37 个业务路径 + `/api/schema/`），在 API 文档中**全部能对应上**，路径与方法一致。逐项核对无"后端有而文档无"的接口。

唯一覆盖差异：backend 分析把 `/api/health/`、`/api/docs/`（Swagger UI）也列入基础设施，而 API 文档只列了 `/api/schema/`（这通常是 schema 自动生成文档的固有特性，不构成矛盾）。

**但 API 文档自身体量声明有误**：开头写"共 28 个路径"，实际列出 **38** 个（经工具统计确认）。属文档内部不一致，建议修正声明数字。

---

## 三、关键不一致 / 矛盾点（按影响排序）

### 🔴 B. 题目状态枚举含"死状态"（最影响前端状态机）
- backend 分析第四节明确指出：`Topic.Status` 中的 `DEDUP_DONE`（查重完成）、`APPROVED`（审核通过）**在视图里从未赋值**，`approve` 直接从 `PENDING_REVIEW` 跳到 `PUBLISHED`，属死状态。
- API 文档却把 `DRAFT/PENDING_DEDUP/DEDUP_DONE/PENDING_REVIEW/APPROVED/REJECTED/PUBLISHED/SELECTED/ARCHIVED` 完整列为 topics 的标准枚举，**未标注任何"不可用"提示**。
- **后果**：前端若按该枚举实现题目状态机/筛选标签，会误以为存在"查重完成""审核通过"两个中间态，与实际流转不符。

### 🔴 C. 动作接口的 request body 被错误生成为"完整资源对象"（影响请求构造）
API 文档由 schema 自动生成，把若干"动作"接口当成了"资源更新"来处理，导致 body 冗余/误导：
- `POST /api/academic-years/{id}/activate/`（动作：设为当前学年）—— body 被生成为要求传完整学年对象（id/name/start_date/end_date/status/is_current 全部"必填"），实际只需路径 id。
- `POST /api/selection-rounds/{id}/open/`（动作：开启轮次）—— body 同样被生成为要求传完整轮次对象（含 id/academic_year/round_no/... 全必填）；而同是动作接口的 `.../close/` 却**正确地没有 body**，两者处理不一致。
- `POST /api/topics/`（创建）、`PUT /api/topics/{id}/`（更新）、`POST /api/topics/{id}/approve/`、`.../submit-review/` —— body 把 `normalized_title`、`created_at`、`updated_at` 标为"必填=是"，但字段说明又写"由系统自动生成"。**自相矛盾**：创建/更新题目实际只需传 title、academic_year、topic_source、proposer、supervisor、description 等核心字段，这些系统字段不应由前端提交。
- `POST /api/topics/{id}/reject/` 的 body 只要求 `comment`（合理），但其响应返回完整 topic 对象（含 normalized_title/created_at/updated_at）——这一条本身合理，仅作说明。

### 🟡 D. 权限信息维度缺失
backend 分析逐接口标注权限，并明确指出 `approve`/`reject` 未加 `IsAdmin`、存在教师自审批越权风险（🔴 高）。API 文档**完全未标注权限**，也未提及该风险。前端无法从 API 文档得知这些接口的权限约束。

### 🟡 E. home/overview 的 todos 现状
backend 分析：`todos` 固定为 `{count:0}`，设计要求的"按角色展示待办"**未实现**。
API 文档：仅描述 `todos` 为 `object`（待办汇总信息），未说明其当前恒为 0 / 功能未实现。前端若据此做待办展示，会以为有真实数据。

### 🟢 F. 路径变量命名差异（等价，非矛盾）
- backend 分析用 `imports/{pk}/`、`imports/{pk}/errors/`；API 文档用 `imports/{id}/`、`imports/{id}/errors/`。仅变量名不同，路由等价，不影响联调。

### 🟢 G. 字段细节（API 文档更全，不冲突）
- login 响应：API 文档比 backend 分析多 `real_name`；me 响应含 `phone/user_status` 等。属 API 文档更详细，不矛盾。
- change-password 响应：API 文档仅列 `detail`（标注"错误信息描述"），未体现"清除 must_change_password 标记"后的状态返回，信息偏少但非矛盾。

## 四、枚举一致性核对（一致的部分）

以下枚举两文档口径一致，可作为前端实现依据：
- `academic_year.status`：DRAFT/PREPARING/IN_PROGRESS/FINISHED/ARCHIVED ✅
- `selection_round.status`：PENDING/OPEN/CLOSED ✅
- `selection_choice.status`：SELECTED/CANCELLED ✅
- `operation_log.operation_type`：CREATE/UPDATE/DELETE/REVIEW/IMPORT/EXPORT/LOGIN/SELECTION ✅
- `import_batch.import_type`：TEACHER/STUDENT；`status`：PENDING/PROCESSING/COMPLETED/PARTIAL_FAILED/FAILED ✅
- topics 列表分页结构 `{count, next, previous, results}` ✅（与项目 MEMORY 约定一致）

## 五、结论与建议

**总体结论**：两文档在"有哪些接口、路径与方法"层面**基本一致、互相印证**（backend 分析的接口在 API 文档中全部存在）；但**契约细节存在多处不一致**，最需警惕的是 **B（题目状态枚举含死状态）** 与 **C（动作接口 body 被错误生成为完整资源对象）**——这两点若被前端照单全收，会直接导致状态机错误或提交多余/错误的字段。

**建议**：
1. 以 `backend-interface-analysis.md` 为业务权威口径，配合实际后端代码，修正 `API接口文档.md`：
   - 把 `topics.status` 枚举加注"实际流转中 `DEDUP_DONE`/`APPROVED` 不会出现"（或按后端意见清理死状态后再同步）。
   - 修正 activate/open 等动作接口的 body（改为仅路径参数，或显式标记"无需 body"）。
   - 修正 topics 创建/更新的 body，移除 `normalized_title/created_at/updated_at` 的"必填"标注（系统生成字段）。
   - 修正开头"共 28 个路径"为实际 38 个。
2. 在前端实现题目状态机/筛选时，**不要**依赖 API 文档枚举中的 `DEDUP_DONE`、`APPROVED`，按 backend 分析的实际流转（`DRAFT/PENDING_DEDUP/PENDING_REVIEW/REJECTED/PUBLISHED/SELECTED/ARCHIVED`）实现。
3. 权限与风险提示以后端分析为准，API 文档补充权限列。
